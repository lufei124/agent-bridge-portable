# 手机 / 电脑会话交接方案

> 目标：不管你在手机还是电脑上打字，都是**同一条对话**，不出现两份互不知晓的历史。

---

## 0. 一句话

**同一个会话，任何时刻只允许一个 Claude 进程持有；每次运行都从文件重新读一遍。**

这两条做到，分叉在结构上就不存在——不是"尽量对齐"，是"没机会分叉"。

---

## 1. 为什么改掉上一版（长驻进程）

我先跑通了长驻进程：`--resume <id> --input-format stream-json`，往 stdin 写一条消息，它带着上下文回答（暗号"蓝色海豚"答对了）。

但长驻进程的代价正是分叉的来源：**内存里有一份可能过期的上下文**。

改成「每条消息一个一次性进程」之后：

- 每次启动必然重读 → 永远不会拿着旧上下文说话
- 进程退出即结束 → 没有"谁还活着"的残留状态
- 不需要维护 stdin 协议、不需要 GC、崩溃了重发即可

代价只是每条消息多 2~3 秒启动时间。对"手机异步聊天"这个场景，完全可接受。

> `src/core/holder.mjs` 保留但不接入主路径，作为"需要长驻/打断"场景的备件。

## 2. 核心规则

| # | 规则 |
|---|---|
| R1 | 一个会话 = 一个 `.jsonl` 文件 |
| R2 | 手机的一条消息 = 一次 `claude --resume <id> -p "<text>" --output-format stream-json` |
| R3 | 同一会话同时只允许一个进程（桥的、或 VS Code 的） |
| R4 | 进程启动时从文件重建上下文 → 新进程天然知道旧的一切 |

R3 是唯一需要主动维持的，其余三条是结构性保证。

## 3. 状态模型（按会话，不是全局）

```
desktop  ──发送时自动接管──▶  phone
   ▲                            │
   └──── 重开标签页 / 巡逻发现 ──┘
```

每个会话在 `state.json` 里存一份：

```json
"views": { ... },
"modes": {
  "<sessionId>": {
    "mode": "desktop" | "phone",
    "since": 1730000000000,
    "lastRunAt": 1730000000000,
    "lastResult": "ok" | "busy-refused" | "taken-over"
  }
}
```

`mode` 只用于**卡片显示和按钮语义**，不作为并发控制依据——真正的依据永远实时探测（进程表 + 文件 mtime）。

---

## 4. 三条巡逻规则

### P1 · 发前检查持有者

手机要发消息时，先问：**这个会话现在有没有别的 claude 进程拿着？**

```
列举 claude.exe 的命令行 → 找 --resume=<sessionId>
  ├─ 有 → 电脑端在用 → 不发
  │      ├─ 会话空闲（>20s 无写入）→ 按钮「强制接管」
  │      └─ 会话正忙            → 只提示「等它跑完」
  └─ 无 → 可以发
```

### P2 · 发前确认空闲

文件最近 20 秒内有写入、或 `inflight` 里有这个会话 → 拒绝发送并说明原因。
**绝不"先发再说"**——那正是上次消息石沉大海的成因。

### P3 · 运行中巡逻

每条消息的进程跑起来后，每 3 秒查一次进程表：

- 出现新的外部持有者 → `kill` 自己的进程，标记为 `taken-over`，卡片提示"电脑端接手了"
- 这样做保证桥不会在电脑已经接手后继续写

---

## 5. 两条交接流程

### 5.1 电脑 → 手机（发消息时自动完成）

```
手机点发送
  → P2 检查空闲 ──忙──▶ 拒绝，卡片说明「电脑端正在跑，等它结束」
  → P1 检查持有者 ──有──▶ 卡片给两个按钮：「强制接管」/「取消」
  → 无持有者、空闲
  → 启动一次性进程（--resume -p）
  → 流式更新卡片
  → 进程退出 → 刷新卡片 + 红点/加急
```

**不做强制接管。** 结束别人的进程是破坏性操作，而且用户就在电脑旁边——让他在电脑上关掉标签页更干净。
卡片给的是「重试」：关掉后点一下，手机上存的原文直接发出去，不用重打。

### 5.2 手机 → 电脑（你什么都不用做，但要重开一次）

回到电脑后：

1. **关掉这个会话的标签页，重新打开** → 新进程 `--resume` → 把手机上的一切读进来
2. 之后你正常打字，桥这边已经退场（每条消息都是一次性进程，没有常驻）

卡片上会写明：

> 📱 手机上的 3 条已写入 · 电脑端关掉标签页重开即可看到

## 6. 检测手段

| 手段 | 实现 | 用途 | 已知局限 |
|---|---|---|---|
| **会话登记表** `~/.claude/sessions/<pid>.json` | 直接读 JSON：`sessionId` / `status`(busy\|idle) / `cwd` / `messagingSocketPath`；进程一退出文件就消失 | **P1 / P3 主判据** | 实测可用，见 §7 |
| 进程表 | PowerShell 过滤 `claude.exe` 命令行里的 `--resume=<id>` | 兜底 | 新建会话命令行里没有 id |
| 文件 mtime | 已有 `TranscriptStore.lastWriteAt` | P2 空闲判断 | 只反映"写过"，不反映"正在跑" |
| 回合状态 | 已有 `isBusy()` + `inflight` | P2 | 800ms 空窗，配合 mtime 使用 |
| 系统空闲 | `GetLastInputInfo`（PowerShell） | 可选：卡片上显示"电脑空闲中，可接管" | 只表示键鼠无输入，不表示人不在 |

进程表用**一个常驻 PowerShell 子进程**每 3 秒吐一行 JSON，避免反复 spawn 的开销。

### 6.1 可能的第三条路：会话之间的消息通道

会话登记文件里还有这些字段：

```json
{
  "pid": 19292,
  "sessionId": "95c3ed75-…",
  "status": "busy",
  "peerProtocol": 1,
  "peerFeatures": ["notify_idle", "artifact_yield"],
  "messagingSocketPath": "\\\\.\\pipe\\LOCAL\\cc-msg-8925…"
}
```

同目录还有个 `<pid>.<hash>.key`，里面是 `peerToken`。

这是 Claude Code 自己的**会话间消息通道**（`SendMessage` 工具走的就是它）。如果桥能说这个协议，理论上可以：**不切换所有权，直接把手机的消息投递给电脑上活着的那个会话**。

那才是真正的零分叉——两个入口、一个脑子，连"接管"都不需要。

但它是内部协议（`peerProtocol: 1`，带 token 鉴权），没有公开文档，跨版本随时可能变。所以**只作为候选记在这里，当前方案不依赖它**。

| # | 验证什么 | 怎么验 | 决定什么 | 需要谁 |

### 已跑完的结果

**E1 ✅ 通过** —— `node tools/oneshot-probe.mjs`

```
建会话（记住暗号：蓝色海豚）
  → 另起一个一次性进程：--resume <id> -p "刚才的暗号是什么？"
  → 退出码 0，回答「蓝色海豚」
  → 文件里追加了完整的 user → assistant 一轮，顺序正确
```

**架构成立**：手机的一条消息就是一个一次性进程，每次启动都重读文件，天然不会拿着旧上下文说话。

**E4 ✅ 顺带确认**：`--replay-user-messages` 要求 `--input-format=stream-json`，一次性 `-p` 用不了 → "消息真的进去了"的确认改为**观察文件**（15 秒内出现这条 user 事件）。

**E2 部分结果**：之前记录的 PID 13656 已经自己消失了，会话登记文件也没了。说明扩展不会长期挂着一个会话进程——但分不清是空闲回收还是你关掉了标签页。

**E3 待跑**：原本要拿 13656 试，它已经不在。等你下次有别的会话开着时再试。

**E6 已绕过**：`~/.claude/sessions/` 是全局的，不区分窗口，所以"多窗口枚举不全"的问题不存在了。

**顺带发现（重要）**：会话登记表能精确回答"谁持有这个会话、忙不忙"，包括新建会话（命令行里没有 id 的那种）。P1 的拦截图就是基于它做的。

## 9. 失败模式

| 情形 | 现在的行为 | 目标行为 |
|---|---|---|
| 电脑端正持有会话 | 发出去被排队丢弃，无任何反馈 | 发送前就拒绝，卡片说明原因 |
| 电脑端正在跑一轮 | 同样静默失败 | 拒绝 +「等它结束」 |
| 电脑端刚跑完 <20s | 可能撞上空窗 | 拒绝 + 提示稍等 |
| 手机连发两条 | 第二条可能撞上第一条 | 进队列，第一条结束后再发 |
| 消息发出去但没落成用户消息 | 不知道 | 15 秒内没看到 user 事件 → 回滚 + 报错卡 |
| 桥的进程跑到一半电脑接手 | 两边同时写 | P3 巡逻 kill 自己，标记 taken-over |
| 电脑端进程被杀 | 错误横幅 | 卡片说明「需重开标签页」，不静默 |

## 11. 验收标准

1. 手机连续发 5 条，电脑端重开标签页 → 历史完整、无重复、无遗漏
2. 电脑端正在跑时手机发 → 明确拒绝，消息留在输入框，不丢
3. 强制接管 → 电脑端出现错误横幅 → 重开后能看到手机的全部内容
4. 桥的进程运行中，电脑端重开标签页 → 桥 3 秒内退场，不覆盖
5. 消息发出去 15 秒内没有成为用户消息 → 卡片报错，不静默

## 12. 风险与边界

- **杀掉电脑端进程**是破坏性操作，只在"你点了强制接管"时执行，绝不自动
- **扩展升级**可能改变命令行参数（`--resume=<id>` 的写法），巡逻会失效 → 需要版本探测 + 告警
- **新建会话没有 `--resume`**，进程表探测不到 → 完全依赖 P2 的写入检测
- 极端竞态（电脑重开标签页后 3 秒内立刻打字）仍可能分叉，窗口约 3 秒
- 每次发送启动新进程，首字延迟约 2~3 秒
